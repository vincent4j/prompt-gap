## 1. 产品目标与最终决策

用户的痛点：多次生成仍不符合预期，却不知道应该重新表达需求、修改提示词，还是更换模型或处理路线。

另一项同等有效的使用目的：用户满意结果，或只是想了解一次生成是怎么完成的，也可以主动查看报告。报告不以失败、投诉或多轮重试为前提；一次成功生成也可查看需求→理解→实际输入→返回结果的完整过程。所谓了解模型工作，限于可观察的调用与结果，不推测黑盒内部推理、内部改写或模型生成机理。

PromptGap 提供三段证据链：

1. **需求理解偏差**：用户原始需求与 Agent 当时的理解是否一致。
2. **提示词覆盖偏差**：理解后的需求是否完整、准确地进入实际提示词、参考素材与参数。
3. **模型执行偏差**：实际请求正确时，生成结果是否满足要求。

一个问题可有多个原因。结论应指出证据支持的最早偏差点，区分事实、推断和无法判断；不能凭一次失败断言模型没有能力。

### 1.1 最终确认的使用原则

- 独立、可移植、可分享，不与 Poster Fit、Eagle、小红书或特定 Provider 耦合。
- 首期必须同时支持 Codex 内置工具和 API 生图，两条路径均覆盖文生图、图生图；任何一条缺失都不能宣称首期完成。
- API 的选择、文档阅读、鉴权、提交、轮询和下载属于现有生图 Agent/Skill；PromptGap 保存任意可见请求与响应，使用每次调用提供的字段关联，不维护供应商适配器名单。新增或更换 API 不应修改 PromptGap 核心。
- 用户通过客户端选择 PromptGap，然后使用数字菜单；无需记住自然语言命令、路径或任务 ID。
- Skill 安装一次；各项目分别开启、关闭留档。项目启用后，对该项目所有图像生成、编辑、返修调用做轻量记录。
- 不设置自动复杂度分类器。简单和复杂调用统一留事实，避免误判导致关键记录缺失。
- 每次调用记录，普通生图不自动生成长报告、不额外进行深度审核。
- 用户可主动查看任何生成任务的过程报告；有偏差时做问题诊断，没有偏差时客观说明过程、需求如何表达及结果如何满足。默认覆盖所选任务的一组尝试，也支持只有一次调用的任务。
- 模型能力研究后置；提出怀疑和依据后，由用户通过菜单选择是否联网研究。
- 关闭只停止未来记录，保留已有任务、图片和报告。
- 事实记录不要求额外评审模型；保存日志不代表将日志反复读入模型上下文。

### 1.2 已被替代、不应重新实现的早期设计

| 早期想法 | 最终处理 |
| --- | --- |
| 每次生成都给用户一份完整审核报告 | 每次留档，主动复盘时交付一份整组报告 |
| 每次生图前联网检查模型能力 | 删除默认调研，改成复盘后的显式可选操作 |
| 枚举复杂度来自动触发深度审核 | 不实施；项目级启用留档、菜单主动诊断 |
| 让用户记住“启用留档”“复盘最近三次”等命令 | 提供状态感知菜单，用户回复编号 |
| 安装 Skill 即可在后台拦截所有生图 | 不作此承诺；Agent 按规则执行，工具接入决定覆盖范围 |
| 引入数据库、追踪平台、完整 UI 或强制预审门禁 | 首期不做 |

## 2. 首期范围与不做事项

### 2.1 首期做什么

- 可安装的 PromptGap Skill、显示元数据、数字菜单。
- 项目启用、关闭、恢复；安全维护 AGENTS.md 中的专属规则块。
- 本地需求版本、任务索引、调用记录、素材保存与校验。
- Codex 内置生图调用前后的记录协议；明确实际可取得字段和缺失项。
- API 同步与异步调用留档：真实请求、参考素材、返回值、轮询、结果下载、错误、重试和回退关联；实现并验证可用接入，不止定义格式。
- 既有生成 Skill/API 脚本接入同一记录协议；项目端只需一次启用，Agent 完成接入检查并报告覆盖范围。
- 初始生成、多轮返修、多图返回、失败、超时、中断的可追溯记录。
- 历史任务分页选择、最近任务复盘、缺失证据提示。
- 三层诊断、图生图目标检查与保留内容检查、人工纠错。
- Markdown 主报告，输入图、输出图、提示词全文、逐项差异与后续菜单。
- 按需模型能力调研方法及项目本地证据缓存；不内置研究平台或爬虫。
- 功能、接续、隐私边界和开销验证。

### 2.2 首期不做什么及原因

| 不做 | 原因 |
| --- | --- |
| 视频审核 | 需要跨帧身份、动作、镜头与音画检查，单独扩展 |
| 文字生成文字审核 | 不是当前核心痛点，先验证图片闭环 |
| 自动优化提示词并反复付费生成 | 复盘不等于授权生成，先输出可执行建议 |
| 自动切换模型或修改项目路由 | 诊断工具不替用户做未授权的生产变更 |
| 替换现有 API 客户端或实现全模型网关 | 首期在现有调用边界留档，保留原有鉴权、模型选择与生成流程；不为所有供应商重写客户端 |
| 独立评审模型和自动审美总分 | 增加费用与延迟，且不能代替具体事实核验 |
| Promptfoo、Opik 等平台强依赖 | 首期本地运行，降低安装和分享成本 |
| 数据库、服务器、浏览器面板、账号体系 | 文件和菜单足够满足首期使用 |
| 自动扫描所有会话和用户文件 | 避免无关上下文、隐私和成本；只处理当前项目及选择的任务 |
| 后台拦截器、Codex 私有 API、未公开钩子 | 当前没有可验证的通用接口，不猜测能力 |
| 防篡改取证系统 | 哈希与版本能检查一致性，不构成安全防篡改保证 |
| 自动删除历史和素材 | 首期保留证据；清理由后续明确策略控制 |
| 自动发布开源仓库或选择许可证 | 当前仓库私有，公开发布与许可证另行决定 |

## 3. 用户交互：选择 Skill，回复数字

### 3.1 客户端入口与安装

用户期望输入 `/P` 后看到 PromptGap 并选择。客户端提供候选列表；Skill 配置 `interface.display_name: "PromptGap"` 和默认进入菜单的提示。

`policy.allow_implicit_invocation: false` 用于保持深度审核显式调用。项目内轻量留档由 AGENTS.md 的短规则和辅助脚本驱动，无需每轮加载完整 Skill。

必须实测当前 Codex 的安装发现和候选入口。文档明确支持显示名和显式 `$skill` 调用，但不能由此承诺客户端一定支持 `/P` 搜索、大小写匹配或某个排序。若当前客户端不支持用户期望的入口，报告真实限制并给出实际可用的 Skill 选择方式，不把手输长命令作为默认操作。

只创建 Skill 文件不会自动完成安装；项目启用也不同于安装。开发时先在临时项目验证；进入用户项目的真实启用属于单独验收步骤。

### 3.2 菜单状态

**未启用：**

```text
PromptGap · 当前项目未启用留档
1. 启用本项目自动留档
2. 查看已有生成任务的报告
3. 查看使用说明
0. 退出
```

选择 1 自动完成项目配置，反馈成功或具体失败原因。无需用户手改 AGENTS.md。

启用时检查当前项目已知的内置工具和 API 入口，记录哪些已接入、哪些无法验证。不要求用户选择技术接入方案；不扫描无关目录，不擅自重构现有客户端。若 API 入口需要项目代码改动，先明确具体文件和影响，按用户已授权范围处理。尚未接入时应显示“部分覆盖”，不能仅因 AGENTS.md 已写入就宣称全部调用均留档。已开启项目新增调用入口时，同样更新覆盖情况。

**已启用且有任务：**

```text
PromptGap · 本项目自动留档已开启
最近一次任务：白衬衫／红砖街区，共 3 次生成
1. 查看最近一次生成任务的报告
2. 选择其他历史任务查看报告
3. 关闭本项目自动留档
0. 退出
```

**已启用但没有记录：**明确显示“尚无生成记录”，提供使用说明、从当前对话补录、关闭和退出，不显示无法执行的最近任务入口。

**已关闭：**显示恢复留档、复盘历史、使用说明和退出。没有历史时同样明确提示。

菜单使用“查看报告”这种中性表述；历史任务可成功、失败或未评价，不按有无问题筛选。无需先增加“学习/排错”选择步骤；用户指定目的时调整重点，未指定则说明过程和符合情况，发现偏差才展开诊断。

### 3.3 历史任务选择

按最近更新时间分页，默认每页 5 项，每项显示标题、日期、调用次数、最近用户反馈；没有反馈写“未记录用户反馈”。不推断满意度。

```text
1. 白衬衫／红砖街区
   9月16日 14:32｜3 次生成｜最近反馈：扣子数量仍不对
2. 灰绿 Polo／室内窗边
   9月15日 10:18｜2 次生成｜最近反馈：材质不满意
6. 查看更早的任务
0. 返回
```

编号绑定当次已展示列表，不因后台新增任务而重新解释同一个编号。下一页和上一页仅在存在时显示。进入另一任务时更新菜单上下文；无效编号重新展示有效选项。

选择任务后默认直接分析该任务的全部尝试。尝试很多时先读摘要和差异，再按需要读取完整证据；不得静默只审查一部分却称整组已审查。

任务边界不清时展示摘要和可用缩略图，请用户按编号选范围。历史未留档的内容只允许显式补录，标记证据缺口。

### 3.4 复盘后菜单

- 查看各次调用完整输入和提示词。
- 若有模型能力疑问：调研当前模型相关能力与测评。
- 返回历史列表或结束。

用户可直接指出“R02 理解错了”“第二张数错了”。保存反馈并新增复盘版本，不覆盖原始需求理解、自检或旧报告。

模型能力调研不以 Agent 已经提出怀疑为必要前提：用户可以主动选择“调研模型能力”，或直接在上下文表达怀疑。菜单可以先列建议项，再提供更多操作，但必须有可发现的入口。

## 4. 自动留档的实际边界

### 4.1 两种职责

**Agent 负责：**捕获相关用户原话、简短执行说明和假设；关联本轮与父尝试；按规则调用记录工具；追加已有自检与用户反馈。

**脚本负责：**创建唯一编号、读写配置、保存请求快照、素材引用或副本、哈希和尺寸、时间与状态、索引、完整性检查。机械工作不使用额外大模型。

不要求记录私有内部推理。执行说明是简短、可审核的任务决定，例如“只改行走姿势，保持人物、服装结构和场景不变”。

### 4.2 Codex 内置生图路径（首期必需）

1. 准备实际生图参数，并保存同一份可访问的参数与需求版本。
2. 创建 `pending` 调用记录，得到 attempt ID。
3. 正常调用内置生图工具。
4. 保存可取得的工具返回信息、原始图像或稳定引用，状态更新为 succeeded、failed 或 unknown。
5. 追加原流程已经产生的自检。发生下一轮返修时记录原因与 parent attempt。

当前已知工具输入包括 `prompt`、`referenced_image_paths` 或 `num_last_images_to_include`；后两者不能同时使用。实现时以当前实际工具声明为准。

优先使用明确文件路径绑定参考图片。若必须使用最近会话图片，记录数量、能够确定的图片身份、顺序及无法确定的项，不能猜出不存在的路径。

工具未返回稳定文件路径或不可访问输出时，记录这一缺口，不能假称已保存原图。实现阶段核对当前工具文档和真实返回；不能仅凭模拟数据宣布内置工具联调成功。

Skill 不能向 Codex 安装后台拦截器。此路径是 Agent 执行协议，可能遗漏整个调用。完整性检查可以发现已有记录的缺项，但无法证明没有完全未记录的调用。报告中必须保留该覆盖边界。

### 4.3 API 生图路径（首期必需）

API 路径必须交付可运行的通用调用前/后记录能力。由现有 Agent/客户端构造请求，并在可见调用边界将同一份有效载荷交给记录器，结束后交付返回或异常。PromptGap 不替换客户端、不管理生成密钥、不新增供应商路由，也不要求用户为新 API 注册适配器。

核心格式分两层：request_snapshot/response_snapshot 保留任意结构的原始可见内容；bindings 由生图 Agent/客户端给出提示词、输入素材、输出素材和可见模型/任务 ID 的字段位置。字段关联按此次调用保存，不形成供应商名单。JSON 可以用 JSON Pointer；multipart 或非 JSON 载荷保留字段/文件清单与稳定素材引用。PromptGap 不凭字段名猜测业务语义。

“无需供应商适配”不等于“自动穿透任何黑盒”：只能拿到外层参数或 stdout 时标记 tool_boundary/summary，不能冒充完整 API 请求；已有脚本若无法暴露内部请求，先说明缺口，再按授权增加导出点。

具体执行：

1. Agent 保存相关需求版本、本轮执行说明与返修原因。
2. 在调用边界记录 API 类型、脱敏 endpoint、请求模型名、实际提示词/消息结构、完整非敏感参数、上传图片顺序、职责及转换过程。
3. JSON、multipart 上传、base64、远程图片 URL 等按真实接口记录；二进制内容写入素材库，记录清单保留关联，不把大段编码写进上下文。远程素材无法取得原始字节时注明证据限制。
4. 保存可取得的响应体（脱敏）、HTTP 状态、Provider request ID、返回模型信息、usage、费用来源和错误；请求模型与实际返回模型分字段，不推测别名背后版本。
5. 同步返回处理图片字节、base64 或结果 URL；异步返回先记录远端 job ID，追加轮询事件，最终获取结果。QUEUED/SUCCESS 等服务端标记不等于图片已保存或审核通过。
6. 远端图片到期前按实际工具权限保存原始产物，并核验文件可读、尺寸与哈希。下载失败保留远端成功与本地未归档两个状态；重试下载不得重新提交生图。
7. 记录原客户端实际发生的重试、回退和取消请求。日志自身不启用重试、不改变现有重试策略；取消请求不等于远端已取消或未计费。

首期交付包含通用 begin/finish/event 记录接口、字段不同的两个 API 合成载荷样例，以及同步/异步记录测试；M4 再选当时可用的真实生图流程验证。现有 API 脚本只是可观察边界的研究样本，不是指定支持对象。供应商文档由负责实际生成的流程按需核对，PromptGap 不新增逐供应商研究步骤，不把 ClawPower 或任何固定 Provider 作为强依赖。

至少完成 API 文生图和图生图的真实成功闭环；同步/异步均完成协议测试，可用环境具备两类入口时分别实测。不具备异步真实环境时明确标记“协议测试通过、异步生产联调未验证”，不能笼统称所有 Provider 已支持。

同一任务允许从内置工具切换到 API 模型，仍以 task ID/parent attempt 关联，复盘显示切换原因和每次实际模型；不拆散为无法比较的历史。

### 4.4 项目接入与失败策略

AGENTS.md 只加入有起止标记的 PromptGap 规则块，不改写其他规则；重复启用不重复插入。关闭通过配置生效，恢复复用原配置。遇到无法可靠辨认的残缺规则块，保留文件并报告冲突。

记录失败不得静默伪装成功。调用前保存失败时提示留档异常，由当前任务规则决定是否继续；首期不另设通用强制生图门禁。已有付费调用完成但收尾失败时，不重新调用模型，保留 pending/unknown 并尝试补齐已有结果。

### 5.3 最低留档字段

| 对象 | 必需内容 |
| --- | --- |
| 项目配置 | 格式版本、启用状态、记录位置、接入方式、内置/API 各入口覆盖状态 |
| 任务 | 唯一 ID、短标题、创建/更新时间、可取得的会话关联 |
| 需求版本 | 相关用户原话、上下文出处、需求 ID、AI 当时理解、假设、用户确认状态 |
| 请求 | attempt ID、parent ID、需求版本、任务说明、调用路径、实际提示词/可见消息角色、请求模型与参数、输入素材顺序与职责、预处理 |
| 素材 | 路径/副本、哈希、可读尺寸和格式、ICC 信息若可取得、来源与是否稳定 |
| 结果 | 调用状态、返回模型、原始响应与输出引用、错误、request/job ID、生成与归档分离状态、时间、费用和 usage 若可取得 |
| 事件与后处理 | 提交/轮询/下载/重试/回退事件、分段时间；已有后处理操作、源/目标哈希及遮罩/参数若可取得 |
| 自检与反馈 | 内容、时间、作者/来源、关联尝试、返修原因 |
| 复盘 | 覆盖范围、证据清单、逐需求检查、归因、置信说明、缺失项和下一步 |

无法取得的字段写 unknown/missing，不用 0 代替未知费用或 Token。不要保存密钥、认证头、Cookie 或带凭据的签名 URL；保存脱敏标记和可用于识别素材的稳定信息。实际提示词中的敏感信息如果需要脱敏，明确标记脱敏版本，不声称它仍是逐字原始副本。

### 5.4 版本、关联与持久化

- 首次生成目标创建任务；后续“重新生成”“扣子不对”等同目标修改归入原任务。
- 新目标创建新任务；不能用全项目唯一“当前任务”绑定并发对话。
- 用户需求变化新增需求版本，各调用引用当时版本；后来的纠错不追溯改写原请求。
- 每次生成请求提交一个 attempt；查询任务状态或下载图片只记该 attempt 的事件，不虚增生成次数。重新提交、回退到另一模型新建 attempt，关联父调用和原因；SDK 内部不可见重试明确标记覆盖限制。一次返回多图共用请求、分别记录输出和检查结论。
- 预调用请求冻结，返回结果和观察按生命周期补齐；结论修订新增复盘版本。
- 稳定素材按哈希复用；临时输入和输出保存副本。引用外部文件时复盘前核验存在性与哈希。
- 索引是派生数据，可以扫描任务重建。使用原子写入、唯一编号和必要的写入保护，防止并发覆盖。
- 失败、超时和中断保留记录；unknown 不自动转为 failed，也不自动付费重试。
- 手工补录必须注明 backfilled、补录时间和证据来源；不能伪装成当时采集。
- 后处理不是新的模型生成，但必须关联模型原图、操作和处理后图片。至少记录原流程已提供的操作事实；不为获取历史缺失信息额外制造一次处理。无法复原时明确指出，不把交付图的错误直接归因于生成模型。

### 5.5 需求与上下文完整性

生图前保留本次相关用户原话及其出处、明确继承的历史要求，需求规格包含目标、硬要求、禁止项、允许自由发挥、优先级、审美偏好和验收方式。不可只保留“重新生成”四个字而丢失它所指的目标。

需求理解状态至少区分 Agent 已记录、用户明确确认、用户纠正；用户未反对不自动伪装成逐项事实确认。不额外增加日常确认环节。多轮简短纠错追加原话并形成相应需求版本。图生图每项参考明确 controls/must_not_control 或同等中文字段。

无法取得完整历史时，在首次记录就标记上下文缺口，复盘只能在该边界内归因。分组和原始事实优先保存，细粒度覆盖矩阵可到复盘时生成，避免每次留档都执行一次完整审核。

## 6. 按需诊断方法

同一套证据既用于过程说明，也用于问题诊断。没有发现偏差时记录“在已核验范围内符合”，不强行分配错误类别或要求继续优化；用户满意属于用户反馈，不替代尚未执行的客观检查。成功一次也不能推断该模型普遍可靠。

### 6.1 首先核对用户要什么

从当时需求版本读取用户原话、Agent 理解和假设。将要求拆为稳定编号的原子检查项，区分用户明确要求、历史继承、Agent 自选、未确认假设。

检查清单以用户需求为主，不能只从提示词提取，否则漏写的要求也会从审核中消失。事后新增解释必须标明为复盘解释。

### 6.2 再核对实际请求

将每项需求映射到实际提示词片段、输入图或参数，标记完整、部分、缺失、冲突、无法判断。检查模型收到的顺序、参考职责、裁剪、遮罩和上传副本。

用错素材属于请求构造问题；如果由理解错误引起，也记录第一阶段原因。模型内部改写不可见时不作推断。

### 6.3 再检查输出

每项写预期、实际观察、对应图片证据和满足程度。图生图同时检查目标修改与必须保留项；不能沿用上一张图的通过结论。

已有自检属于当时判断，不自动当成正确事实；复盘可以纠正它。低清、遮挡或视觉难以判别时写无法判断，不猜测数量、纹理等细节。

### 6.4 归因与行动

- 保留三个主类别，可增加输入、参数、传输、约束冲突等子类型。
- 区分“发现偏差”和“证明根因”；没有当时理解记录时，可能无法区分理解遗漏和提示词遗漏。
- 连续未遵循明确请求可以支持模型执行风险，不足以证明模型完全不具备能力。
- 对比多次尝试时记录变动轴和固定项；不能把同时改很多变量的结果当作因果实验。
- 图像经过后处理时区分模型原始输出和后处理结果，避免把后处理错误归给模型。
- 输出建议应具体到补充哪项需求、修改哪段请求、补哪个输入，或为何值得调研模型能力。
- 报告不自动修复、不自动再生图。用户后续授权后，由原生成流程执行。
- 分别给出需求理解、提示词覆盖、输出符合程度三个结论；“提示词正确”不能代替图片通过。逐项满足程度和根因类别分开，避免把“无法观察”误写为“模型失败”。
- 每轮关联已解决、新增和仍未解决的问题；建议下一步时说明修改轴、需要保留的正确项及为什么有新增信息。不得把重复加重措辞当作默认解决方案。

## 7. 模型能力调研：用户选择后执行

发现执行限制嫌疑时，先说明已有证据和不确定项，再在菜单提供调研入口。普通生成和首次复盘均不默认联网。

研究范围限定为准确模型/版本、Provider 路由与某项关键能力；官方接口支持、独立测评、项目实验分开引用。评估来源方法、发布日期、任务匹配程度和版本一致性。

输出分为：明确不支持、支持但相关表现不稳定、没有足够证据。一般物体计数测试不能直接证明小扣子保真；偏好总分不能证明商品结构准确。

按模型版本和能力类别缓存原始链接、获取日期、结论及限制。版本变化、证据陈旧或实际表现矛盾时才刷新。涉及联网使用当前环境可用且已授权的工具；不把某个插件设为硬依赖。

研究预算建议：先用 2～5 分钟进行有限查询；论文级交叉验证可能超过 10 分钟，作为扩大研究范围的后续选项。这些是计划预算，不是实测保证。未找到直接证据时停止并明确说明，不能无限搜索。

## 8. 人工 Review：只以 report.md 为主入口

用户最新纠正：即使成功案例也必须按完整模板展示，才能理解 AI 外部工作过程与逐节点数据流转。取代此前“一屏至一页摘要”的限制：report.md 是完整、自足的初始入口，不能把核心过程藏进 details.md。用户无需阅读底层 JSON 或来回跳文件补上下文。

主报告阅读顺序固定：

1. **逐次执行概况**：本次完成了什么或具体哪里不符。
2. **用户原话与当时理解**：包含历史继承、自由选择及假设，明确缺口。
3. **实际输入与返回**：完整提示词和解释、图片与职责、参数、输出图与响应；自检和反馈单独标明。
4. **节点流转与审核**：每项要求如何从原话进入理解、实际请求及结果；展示观察、依据、风险与下一步。
5. **全局结论**：在完整过程后汇总，不以结论替代事实。details.md 作为兼容的逐次过程入口，不作为阅读主报告的前置条件。

主报告与逐次详情都保留全量实际提示词、用户原话、当时理解及输入输出原图，不能以摘要替代。共享报告使用相对资源引用；Codex 对话展示本地图片时使用该客户端要求的绝对路径。

**详情页必须以执行次数为主线，不按“全部需求／全部提示词／全部结果”分散叙述。** 每次独立章节按以下顺序连贯说明：

1. 本次执行概况：有问题先写具体问题；没有问题先说明完成了什么，不捏造问题。标题使用“第一次执行：……”而不是固定“第几次失败”。
2. 用户当时要求什么：原始要求、此前纠正、当前完整目标；不能只写“同上”。
3. Agent 当时怎么理解：引用当时记录，区分事后重建及缺失。
4. 最终传给模型什么：完整提示词原文和中文解释、实际输入图、顺序及职责、相关参数；明确文生图是否根本没传上一轮图片。
5. 返回什么：输出图、实际返回文字或错误；单独标注 Agent 自检，不能冒充模型回复。
6. 对照这一次的完整过程，说明哪些要求得到满足、哪些未满足及依据。成功案例不强行归因；有后续调用再解释用户反馈或继续尝试的原因。

主报告和详情都先按执行顺序连贯叙述，不能先放跨轮结论表、覆盖表再要求用户来回拼事实。内部覆盖矩阵仍可保留在结构化数据；成功和失败只改变结论，不改变过程完整度。

默认用中文解释；实际提交的提示词保持原始语言、文本及可见消息结构。非中文提示词提供简明中文解释，明确区分解释与实际发送原文。报告还需展示本次审核采用的方法、每项依据、剩余风险和局限，而不只给归因标签。

无图片的失败调用同样进入过程表，按输入/传输/服务错误分析，不能执行不存在的视觉审核。跨内置工具和 API 的尝试在同一报告内展示，注明各自证据可见性。

需要对照图时仅做确定性等比缩放、裁剪和拼接，标注裁剪区域，不修改证据内容；保留原图。报告首部注明审核范围、记录方式、是否补录和重大缺项。

## 9. 时间和 Token 控制

- 日常仅加载项目短规则和必要记录说明，不读取 diagnosis/model-research 全文。
- 记录实际请求和文件使用脚本，不额外调用模型生成日志。
- Agent 只额外写简短执行说明；复用已有自检，不为留档再评图。
- 日志输出只返回编号和保存状态，不回显整份请求、图片编码或历史。
- 需求和素材复用版本/哈希；提示词每轮完整保存，分析时优先读取差异。
- 菜单只读索引，复盘才加载选择的任务；不得声称未查看的图片已审查。
- 优先查看原图整体与必要细节，避免反复加载所有高分辨率素材。
- 对照板和长报告在复盘时生成；研究不默认进行。
- 留档不增加远端素材上传或独立评审调用。磁盘读写、素材复制和哈希仍有实际耗时，需要实测。
- API 出图已有下载过程时直接复用文件；若原流程只留临时 URL，为保存证据需增加下载，该网络与存储开销单列，不能声称全部只是本地读写。

第一版记录脚本耗时、Agent 额外步骤、素材新增存储，以及环境可取得的 Token/费用。无法准确分离模型 Token 时报告可观测范围，不编造节省比例。

开销验收以“没有额外模型调用、没有全日志上下文回灌、重复素材不复制、菜单不扫描全量图片”为硬条件；具体秒数以小图和高分辨率样本实测后记录。不要以未经验证的固定延迟承诺替代证据。

## 10. 分阶段实施计划与工作量估算

### 里程碑执行边界

用户要求分别实施、分别验收。原阶段作为内部任务保留，交付按以下四个里程碑组织；完成一个里程碑后停在验收点，不自动连续做完整项目。

| 里程碑 | 包含原阶段 | 用户收到什么 | 时间估算 |
| --- | --- | --- | --- |
| M1 记录协议与报告样例 | 阶段 0＋1 | 内置/通用 API 留档边界、数据协议、完整合成复盘样例、已知限制 | 2～4 小时 |
| M2 自动留档与数字菜单 | 阶段 2＋3 | 可操作的项目开启/关闭、内置/API 记录、历史选择；功能及协议测试 | 6.5～11 小时 |
| M3 完整复盘能力 | 阶段 4 | 三层诊断流程、报告生成、纠错版本、能力研究菜单 | 2～4 小时 |
| M4 真实联调与交付 | 阶段 5＋6 | 内置/API 文生图及图生图真实验证、开销报告、安装与交接 | 3.5～6 小时 |

M1 核实可见留档边界和通用记录格式，不核定供应商支持名单。客户端 UI 发现与真实图片返回是否可归档必须留到 M2/M4 实测，不能以文档核实冒充运行验证。M1 不付费生图、不修改现有生成脚本、不安装到使用项目。

估算为单 Agent 连续有效工作的范围，包含对应阶段自测；不等于交付承诺，不含用户 review 等待、服务故障和生图模型排队。遇到未公开客户端能力或工具返回限制，先报告证据并调整实现，不按估算强行宣称完成。

| 阶段 | 完成内容 | Agent 做什么 | 本阶段不做及原因 | 估算 |
| --- | --- | --- | --- | --- |
| 0 记录边界核实 | 确认 Skill 元数据、内置工具可见字段、通用 API 记录边界 | 读工具声明及调用样本，明确原始快照与字段关联职责 | 不维护供应商名单、不猜 Codex 内部钩子、不付费探测 | 1～2 小时 |
| 1 数据协议与完整报告样例 | 确定记录格式、三层诊断、任务分组；做可 Review 的整组样例 | 创建明确标注的合成案例或证据完整的历史案例，生成示例报告 | 不把历史缺口补成事实；不做新生图 | 1～2 小时 |
| 2 轻量留档与 API 接入 | 启用/关闭、需求版本、媒体去重、索引、API 同步/异步事件与接入样例 | 实现辅助脚本、调用边界接入、下载与重试关联、持久化测试 | 不做全 Provider SDK、数据库和后台服务 | 5～8 小时 |
| 3 Skill 与数字菜单 | 显式入口、项目状态、历史分页、关闭恢复、AGENTS.md 规则块 | 编写 Skill/菜单、安装配置；在临时项目验证幂等启用 | 不改客户端 UI，不保证未经验证的 /P 行为 | 1.5～3 小时 |
| 4 复盘与报告 | 原话→理解→请求→结果的证据映射、图生图保留检查、归因、纠错版本 | 实现报告辅助生成、诊断指令、按需能力研究说明与缓存格式 | 不自动调用外部评审，不自动换模型重试 | 2～4 小时 |
| 5 内置工具＋API 双路径联调与开销验证 | 两条路径的文生图/图生图、跨路径返修、异步事件、图片与报告可用 | 先协议与故障测试，再按授权执行两条路径真实联调；分别测开销 | 不把模拟或单路径通过当双路径完成；无生成授权不产生新费用 | 3～5 小时 |
| 6 发布前整理与交接 | 可安装包、使用说明、测试证据、限制和续接记录 | 检查无私人素材/凭据、安装发现、最终文档一致性 | 不自动公开仓库或选许可证 | 0.5～1 小时 |

**总计：约 14～25 小时有效工作量。** 相比 v1.0 增加 API 实际接入及双路径验证。阶段 1 完成即可先看到完整报告样例；阶段 3 完成可演示菜单和模拟留档；阶段 5 两条路径均完成对应真实验证后，才可称首期生图接入完成。实际耗时在每阶段结束回填。

### 10.1 阶段 0：证据与接口

参考：本机 `skill-creator/SKILL.md` 与 `references/openai_yaml.md`、当前 image_gen 工具声明、仓库 README。Skill 路径属于当前开发环境，不能写成发布包的硬依赖。

只读查看现有 API 客户端，了解实际请求/响应在哪个边界可取得；这是记录可行性证据，不是供应商能力认证。用不同字段的合成载荷验证记录协议无需修改核心；真实调用选型及其官方接口核对由执行生图的流程在 M4 按需完成。

已读取的元数据文档支持 `display_name`、`short_description`、`default_prompt`、`policy.allow_implicit_invocation`。默认提示需显式提到 `$prompt-gap`。不由此推断客户端支持后台生命周期钩子。

验收：列出真实可用字段和未知输出；开发阶段再次核实变化；安装入口验证单独留证据。

### 10.2 阶段 1：协议与样例

先固定需求 ID、需求版本、parent attempt、结果状态、缺失字段和报告阅读顺序。样例覆盖三轮：需求误解、请求遗漏、明确请求未执行，并区分事实与推断。

验收：用户无需阅读 JSON 即可找到每次提示词、图像、修改原因和归因证据；无证据时显示无法判断。样例反馈影响后续实现；未新增阻断意见时可按已批准范围继续。

### 10.3 阶段 2：记录核心

命令接口在实现时定稿，但至少支持项目启用/关闭、任务与需求版本创建、调用开始/完成/异常记录、观察追加、任务列表、完整性检查和索引重建。

API 接入必须提供可运行样例，演示同一请求发送前留档、实际响应后收尾、异常保留。同步/异步均覆盖协议测试；原始响应与素材解码/下载结果关联，API 凭据不得写入证据包。

验收：请求逐字往返、素材顺序保持、重复完成不覆盖冲突结果、并发任务不串组、文件中断不破坏已有数据、未知费用不写零、缺图可检测。

### 10.4 阶段 3：菜单与项目启用

通过脚本读取状态，Agent 展示动态菜单。维护 PromptGap 专属 AGENTS.md 标记块与必要忽略规则；重复启用、关闭恢复不产生重复内容。默认不创建无关项目文件。

验收：空项目、已有 AGENTS.md、已启用、已关闭、零记录、多页历史和无效选项都可执行；关闭不删除记录；菜单数字始终对应已展示对象。

### 10.5 阶段 4：诊断与报告

从需求而非提示词生成检查项；先检查记录完整性，再做覆盖和图像检查；输出可核对证据。机器辅助处理差异与模板，Agent 作语义和视觉判断。

验收：第一阶段错误不会被漏到第二阶段；三层原因可并存；缺当时理解时不能武断归因；目标改对但保留区损坏判失败；用户纠错保留旧版。

### 10.6 阶段 5：真实联调

分别验证内置生图和 API 调用前后能够取得什么、图片是否落地、输入路径是否准确、模型信息是否可见。至少完成四个真实成功用例：内置文生图、内置图生图、API 文生图、API 图生图；可以在小型连续任务内复用素材并验证跨路径关联。同步/异步协议和故障测试不等于真实生产接口测试；两类实际环境可用时补齐相应联调。已有真实记录可复用验证读取，但不能替代尚未验证的真实入口。

使用测试素材与临时项目；不重开已冻结商品。任何需要新计费生成的测试遵循当时明确授权，没有授权时只完成非付费部分并标明真实验证待办。

验收：真实生成结果能从报告打开；记录正确关联；中断不触发重复调用；留档不会新增评审模型调用；记录实测时间与可见 Token 范围。

### 10.7 阶段 6：最终验收

运行 Skill 结构验证与有意义的行为测试；核查所有链接和媒体引用；在新上下文从本文及记录恢复任务。报告实际通过、部分通过和未验证项。

README 更新为最终按需复盘定位；当前 README 中“调用后提供完整报告”需澄清为调用后记录、主动复盘时报告。未完成前不宣称产品可用。

## 11. 必须覆盖的验收案例

| 案例 | 期望结果 |
| --- | --- |
| 用户原话被理解错 | 指出第一阶段证据 |
| 用户查看一次成功生成的过程 | 菜单可选择，完整串联原话、理解、输入与返回，不强行找错或要求返修 |
| 用户满意但部分事实无法核验 | 分开记录满意反馈与证据缺口，不推断全部客观检查通过 |
| 用户想了解模型如何工作 | 说明可观察流程与输入输出，不编造内部推理或把一次成功当能力证明 |
| 理解正确、提示词遗漏 | 指出第二阶段缺失及对应原话 |
| 请求完整、结果反复未执行 | 第三阶段疑似限制，不能宣判没有能力 |
| 参考图错序、少传、上传副本裁错 | 请求构造问题，可回溯实际素材 |
| 只改姿势却改变衣服 | 目标与保留项分别检查 |
| 遮挡、低清、缺原图 | 无法判断，不编造事实 |
| 一次返回多图部分失败 | 逐图结论，不以一张代表全部 |
| 超时或中断 | pending/unknown 可发现，不自动付费重试 |
| 完全未记录的历史调用 | 不承诺可检测，补录注明限制 |
| 同项目多对话并行 | 不共享错误的当前任务 |
| 用户需求中途变更 | 新需求版本，不倒改历史 |
| 用户纠正 Agent 数错细节 | 新反馈与新复盘版本 |
| 素材移动或被改写 | 缺失/哈希不一致可见 |
| 历史索引损坏 | 从任务记录重建 |
| 重复启用、关闭恢复 | 不重复规则，不丢数据 |
| 简单生图 | 只留事实，无长报告与能力研究 |
| 主动研究模型能力 | 有来源、版本、适用边界；预算内无证据则停止 |
| API 同步 JSON/base64/URL 返回 | 真实请求与响应关联，图片原始字节保存，格式和哈希可核验 |
| API 图生图 multipart、多图与遮罩 | 图片顺序、上传副本、职责、遮罩和参数准确记录 |
| API 异步提交、轮询和下载 | 同一 attempt 串联 job ID 与事件，轮询不计新生成 |
| API 远端成功但下载失败 | 保留成功与归档失败两种事实，仅重试下载 |
| API SDK 重试或模型回退 | 可见的重新提交分别记录，隐藏重试标注限制，不能重复计费推断 |
| 换成字段不同的新 API | 原始快照保留，bindings 随调用传入，核心不增加供应商分支 |
| 内置与 API 混合返修 | 同一任务内模型、路径、父调用和变动原因可比较 |
| 部分入口未接入 | 菜单/配置明确部分覆盖，不宣称全部自动留档 |
| 后处理改变正确原图 | 原图与处理图区分，原因不错误归到模型 |
| 用户主动怀疑模型能力 | 无需等待 Agent 先提出怀疑，也能通过菜单启动调研 |

## 12. 用户与 Agent 的责任

Agent 完成方案、开发、临时环境验证、记录脚本、菜单、报告、缺陷修复、耗时测量和交接。用户无需手写 AGENTS.md、维护日志或输入路径/ID。

用户负责最终方案 Review、需要时选菜单、纠正主观预期、决定是否做额外能力研究，以及尚未授权的付费测试或对外发布。不要把常规实现选择逐项交回用户。

M2 交付后用户要求继续，本轮授权推进 M3；完成后停在验收点。该授权不自动扩展为安装到所有项目、新的付费生成、提交推送或公开发布。每个里程碑内按范围推进，不为常规实现选择反复索要许可。
